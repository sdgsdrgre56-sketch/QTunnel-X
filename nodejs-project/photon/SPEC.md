# Фотон v1

Протокол «клиент ↔ свой сервер». Своих шифров нет: X25519, HKDF-SHA256, ChaCha20-Poly1305. Внешнего аудита нет, поэтому протокол дополнительный.
Один и тот же поток байтов (рукопожатие и кадры) идёт поверх двух транспортов:
- **TLS 1.3 / TCP** — `proto.js`, `transport.js` (Node.js, проверено тестами);
- **QUIC** — `quic/` (Go, quic-go; **не собиралось и не запускалось**, см. ниже).

## Что известно клиенту
Из ссылки: адрес и порт, постоянный открытый ключ сервера `S` (X25519), токен пользователя (16 байт), отпечаток SHA-256 сертификата сервера.

## Рукопожатие (на каждое соединение / поток)
Обозначения: `HKDF(ikm, info, n)` — HKDF-SHA256 с пустой солью; nonce AEAD = 4 нулевых байта ‖ счётчик (8 байт, big-endian).

Клиент → сервер:
```
epk(32) ‖ len(2) ‖ AEAD(k1, nonce=0, aad=epk, ts(8) ‖ token(16) ‖ plen(2) ‖ pad)
k1   = HKDF(X25519(esk, S), "photon/1 hello", 32)
len  = длина шифртекста, big-endian, XOR с HKDF(k1, "photon/1 len", 2)
ts   = unix-время в секундах, pad — случайные 0..95 байт
```
Сервер считает `k1 = HKDF(X25519(S_priv, epk))`, читает `len`, расшифровывает, проверяет:
время (разбег не больше 30 с), токен, и что такой `epk` не встречался последние 60 с (защита от повтора).
Любая ошибка → сервер отвечает как обычный веб-сервер (HTTP 404 nginx) и закрывает соединение.

Сервер → клиент: `eps(32)` и сразу кадр `"OK" ‖ pad`.
```
ikm  = X25519(esk_c, eps) ‖ X25519(esk_c, S)      (сервер: X25519(esk_s, epk) ‖ X25519(S_priv, epk))
salt = SHA256(epk ‖ eps)
c2s  = HKDF-SHA256(ikm, salt, "photon/1 c2s", 32)
s2c  = HKDF-SHA256(ikm, salt, "photon/1 s2c", 32)
```
Первый кадр сервера расшифровывается ключом `s2c`: так клиент убеждается, что сервер знает `S_priv`.

## Кадры
Каждое направление имеет свой ключ и свой счётчик nonce (общий на все операции этого направления):
```
кадр = AEAD(key, ctr++, len(2)) ‖ AEAD(key, ctr++, data)      len ≤ 16384
```
## Запрос
Первый кадр клиента: `atyp(1: 1=IPv4, 3=имя, 4=IPv6) ‖ адрес ‖ порт(2) ‖ plen(2) ‖ pad`.
Ответ сервера одним кадром: `0` — подключились, `1` — не вышло. Дальше обычный поток в обе стороны.
UDP пока не поддерживается.

## Чего в Фотоне нет (честно)
- Нет защиты от анализа по длине пакетов и по времени, кроме случайного дополнения в рукопожатии.
- Нет постквантового обмена (ML-KEM-768 можно добавить вторым общим секретом в `ikm`).
- Клиент не проверяет настоящий сертификат: только отпечаток из ссылки (так же, как для самоподписанного режима остальных протоколов).

## QUIC-версия
`quic/main.go` пишет те же байты в поток QUIC (один двунаправленный поток = одно проксируемое соединение, рукопожатие на каждый поток).
Она написана без возможности собрать: в этой среде недоступны Go-модули. Перед использованием:
```
cd photon/quic && go mod tidy && go build -o photon-quic .
```
Затем проверить совместимость с Node-стороной (клиент Go ↔ сервер Node и наоборот), этого я не делал.

## Antohin (постквантовый режим, photon/2)

Antohin — отдельный протокол в Квазаре: свой порт, ключи, токен, сертификат и служба (`quasar-antohin`), режим `pq: "only"`. Код общий с Фотоном, поэтому режим сервера можно задать в конфиге: `pq: "allow"` (по умолчанию для ручного запуска) принимает оба, `"only"` — только Antohin, `"off"` — только v1. Режимы различаются длиной приветствия (диапазоны не пересекаются).

- Клиент: к открытому тексту приветствия добавляется ключ инкапсуляции ML-KEM-768 (1184 Б) в конце, после `pad`; всё это внутри AEAD, снаружи видны только случайные байты.
- Сервер: проверяет ключ (длина, коэффициенты < q), инкапсулирует и отвечает `eps | AEAD(k2, ct_mlkem)`, где `k2 = HKDF(DH1 ‖ DH2, "antohin/1 stage")`. Шифртекст ML-KEM снаружи не виден.
- Итоговые ключи: `HKDF(DH1 ‖ DH2 ‖ ss_mlkem, SHA256(epc ‖ eps ‖ ek ‖ ct), "antohin/1 c2s|s2c")`. Секрет надёжен, пока устойчив хотя бы один из двух примитивов (X25519 или ML-KEM).
- ML-KEM-768 реализован в `photon/mlkem.js` (FIPS 203), сверен с Go `crypto/mlkem` (`tools/mlkem-xcheck`). Внешнего аудита нет.
- Чужой или неверный клиент получает тот же ответ nginx 404, что и в v1.
